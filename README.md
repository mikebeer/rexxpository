# RXPIP — a package manager for REXX

RXPIP is a pip-style package manager for classic REXX programs. It has two
halves:

- **Server** (`server/rxpip_server.rexx`) — a CGI script that serves a
  package repository over HTTP(S). Runs under Apache/mod_cgi on
  `www.rexxpository.org`. Written once, in Regina — see
  [ARCHITECTURE.md](ARCHITECTURE.md) for why one server implementation is
  enough to support every REXX runtime.
- **Clients** — the command-line tool developers run locally to install,
  publish and use packages. One per REXX family, same commands and
  messages everywhere:

  | Runtime | Client | Packages it installs |
  |---|---|---|
  | Regina | `client/rxpip.rexx` (`regina -a`) | classic REXX source, `SOURCE/any` |
  | ooRexx | `client/oorexx/rxpip-oorexx` | the same classic packages (shared store) |
  | NetRexx | `client/netrexx/rxpip-netrexx` | NetRexx source (`.nrx`), `SOURCE/netrexx` |
  | cREXX | `client/crexx/rxpip-crexx` | cREXX Level B source (`.crexx`), `SOURCE/crexx` |

  Configuration and credentials (`~/.rxpip/config.txt`, `credentials.txt`)
  are shared by all clients; each language keeps its own installed
  packages (Regina and ooRexx share one set).

A REXX program declares what it needs with a comment convention:

```rexx
/* REQUIRE mathutils */
/* REQUIRE greetutils */
```

and `rxpip run yourprogram.rexx` resolves and installs anything missing,
then runs it.

## Quick start

**Linux / macOS:**

```bash
export RXPIP_HOME=~/.rxpip          # optional, this is the default
rxpip config set REPO_URL https://www.rexxpository.org/cgi-bin/rxpip_server.rexx
```

`client/rxpip.rexx` is executable and has a `#!/usr/bin/regina -a`
shebang, so `chmod +x client/rxpip.rexx` and running it directly
(`./rxpip.rexx ...`) works, or invoke explicitly with `regina -a
client/rxpip.rexx ...`. The `-a` matters — see the note on argument
handling in ARCHITECTURE.md.

**Windows:**

```powershell
set RXPIP_HOME=%USERPROFILE%\.rxpip     REM optional, this is the default
rxpip config set REPO_URL https://www.rexxpository.org/cgi-bin/rxpip_server.rexx
```

Use `client/rxpip.bat` (put it on `PATH` alongside `rxpip.rexx`, or run
it from the `client\` directory) so plain `rxpip ...` works the same
way as on Linux/macOS. Needs Regina for Windows on `PATH`, plus
`tar.exe`/`curl.exe` — both ship in `System32` on Windows Server 2019+
and Windows 10 1803+; on older hosts, Git for Windows bundles
compatible versions of both. See DEPLOY.md's Windows testing section
for a checklist — the Windows code paths are implemented but, absent a
Windows host during development, not yet executed, so please verify
before relying on them.

Once configured (either platform):

```bash
# use a package manager
rxpip search math
rxpip show mathutils
rxpip install mathutils
rxpip install greetutils==1.0.0
rxpip list
rxpip freeze > requirements.txt
rxpip uninstall mathutils

# the REQUIRE workflow
rxpip run myprogram.rexx arg1 arg2      # auto-installs deps, then runs
rxpip build myprogram.rexx --output=out.rexx   # same, but writes a
                                                # standalone file instead
                                                # of running it

# accounts and publishing (accounts are approved by the repository admin:
# request one on the web page, or ask for an invite code)
rxpip register --user=anna --invite=<code>      # saves your token locally
rxpip login --token=<token>                     # or log in with an existing token
rxpip publish mypkg-1.0.0.rxpkg \
  --name=mypkg --version=1.0.0 --author=me \
  --summary="what it does" --requires="otherpkg>=1.0.0"
rxpip token new --label=ci | list | revoke <id>  # manage your API tokens
rxpip owner add|remove|list mypkg [user]         # who may publish mypkg
rxpip publish mypkg-1.0.0.rxpkg --name=mypkg --version=1.0.0 --private   # hidden from the public
rxpip visibility mypkg [public|private]          # show / change (owners)
rxpip reader add|remove|list mypkg [user]        # who else may read a private package
rxpip whoami | logout
```

`rxpip help` lists every command.

## Web front end

The server's root page (`https://www.rexxpository.org/`) is a read-only
package index with search; each package has a page with the install
command, owners, requirements, versions and download links for every
artifact. It is plain server-rendered HTML (no JavaScript, no cookies).

## Accounts, tokens and ownership

Publishing needs an account. People can **request** one on the web page
(`?action=SIGNUP`: name, e-mail, location); the administrator gets a mail
with a review link, approves or rejects, and an approval mails the
applicant a single-use invite code. Invites can also be created directly
(`rxpip_server.rexx admin invite`). Tokens are
generated by the server and shown once, and only a salted hash is kept.
The first publish of a package name makes you its owner; owners can add
other owners. Releases are immutable. Details and the operator commands
are in [DEPLOY.md](DEPLOY.md) §8.

## Client updates, statistics and administrators

Clients send a short `X-Rxpip-Client: regina/1.2.0 (linux)` note with every
request. `rxpip update [--check]` fetches the newest release of your kind of
client from the server and replaces the client files (HTTPS only); once a day
`install`/`search`/`show`/`run` print a hint when a newer release exists
(`CLIENT_CHECK off` disables it, `AUTOUPDATE 1` installs it automatically).

The server keeps a daily usage log (`repo/.stats/`): time, action, client
kind/version/OS, a per-day pseudonymous id (no addresses, no tokens), and
which packages are downloaded. It is **not public**: only administrators
(`admin addadmin <user>` on the server) can read it, with `rxpip admin stats
[--days=N]`; they can also `rxpip admin users`, `lock <user>` and publish
client releases with `rxpip admin client-publish <kind> --version=V <files>`.
`RXPIP_NOSTATS=1` turns the recording off. See DEPLOY.md and the manual.

## Tests

`tests/run_tests.sh` starts a CGI harness (behaves like Apache) and runs
180 end-to-end checks against the real server and the Regina client over
HTTP (needs `regina`, `curl`, `tar`, `python3`).

`tests/run_client_matrix.sh` runs one identical scenario (register,
publish, dependencies, install, run with arguments, tokens, owners, …)
against every client found on the machine — Regina, ooRexx, NetRexx
(`NETREXX_JAR=…/NetRexxC.jar`, needs Java) and cREXX (`rxc`/`rxas`/`rxvm`
on the PATH) — and skips the ones that are not installed.


## Where packages are installed

`install`, `uninstall`, `list`, `freeze` and `scan` work on the **current
directory** by default: the package files are copied into it and a record of
what was installed goes to `./.rxpip/installed.txt`. Use `--global` (`-g`) for
the shared store in `~/.rxpip`, `--target=DIR` (`-t DIR`) for another directory,
and `--force` to overwrite a file rxpip did not install. `run` and `build` use
the shared store.

`rxpip find [dir...] [--sync]` finds all installs below the given directories
(default: the current one) plus the shared store, shows packages that exist in
several places and which copies are older; `--sync` brings them up to date.

## Why `rxpip run`/`rxpip build`, as well as `install`?

Regina and ooRexx find an external routine by file name: a call to `Square(7)`
runs the file `Square.rexx` (or `.rex`) found in the current directory or on
the `PATH`. That works for a package whose files each hold one routine and are
named after it, and such a package can be used straight from the directory it
was installed in. It does not work when one file holds several routines, or
when a routine in one file needs a label in another.

`run` and `build` solve this the portable way: they concatenate your
script's source with a safety `EXIT` and then the source of every
installed package file, producing one ordinary, self-contained REXX
program where every required routine is just another internal label.
This works identically on any classic-REXX interpreter — no OS-specific
search-path tricks, no shell involved, no per-call process spawning.

See [ARCHITECTURE.md](ARCHITECTURE.md) for the full design writeup,
including a documented (but deliberately *not* used) alternative — REGINA
does have a PATH-based external-command fallback, but it turns out to be
shell-injection-vulnerable and unreliable in ways that make it unsuitable
for a general-purpose package manager. Worth knowing about; not what
RXPIP uses.

## Package format

A package is a `.rxpkg` file — a plain `tar.gz` of one or more `.rexx`
source files:

```
mathutils.rexx
```

```rexx
/* mathutils.rexx */
Square: procedure
  parse arg n
  return n * n
```

**Gotcha to know about:** don't name an exported routine the same as a
REXX built-in function (`Reverse`, `Date`, `Random`, …). REXX identifier
lookup is case-insensitive and checks routine labels *before* built-ins,
so a routine called `Reverse:` silently shadows — and recursively calls —
the built-in `REVERSE()`, which segfaults the interpreter. We hit this
exact bug writing the example packages; see `examples/strutils/`.

## Status

Everything above is implemented and was tested end-to-end against a real
HTTP server (Python's CGI handler standing in for Apache during
development; behavior against Apache itself is covered by
[DEPLOY.md](DEPLOY.md)'s notes on header forwarding and process
ownership). Supported today: Regina, ooRexx 5.x, NetRexx 4.x and cREXX
1.0 beta 3 — each tested by the client matrix. Windows/macOS paths of the
NetRexx, cREXX and ooRexx clients have not been run (only Linux was
available); see ARCHITECTURE.md §8.
